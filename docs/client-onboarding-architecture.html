Onboarding a New Client

Architecture, steps and requirements — as the repo actually implements them.

1 · Isolation model

One VM per customer, per environment. Not a shared multi-tenant cluster. The schema is tenant-aware and TENANT_MODE supports multi, but provisioning always writes TENANT_MODE=single.

intellicore-acme-staging
e2-standard-2 · own IP · own DB
intellicore-acme-production
e2-standard-4 · own IP · own DB

Buys: hard data isolation, no query-scoping bugs possible, per-customer billing, blast radius of exactly one customer.  Costs: spend scales linearly — no pooling.

4 · The steps  — 15–25 min per environment

  1. Reserve static IP → derive <ip-with-dashes>.sslip.io No DNS work required — sslip.io resolves it, Caddy gets a real LE cert for it.
  2. Open firewall :80 and :443 :80 must be reachable — Let's Encrypt needs it for the HTTP-01 challenge.
  3. Create VM — Ubuntu 22.04, 50 GB pd-balanced, Docker via startup script
  4. Wait for Docker — polls 30 × 10 s
  5. Package repo at HEAD and scp to the VM
  6. Generate secrets — Postgres, Neo4j, JWT, credentials, admin password Generated on the operator's machine so the admin password can be printed once.
  7. Write .env.prod (chmod 600) → docker compose up -d --build
  8. Bootstrap admin via scripts.create_admin
  9. Verify — login, TOTP enrolment, paste BYOK key, download a PDF report
Run once with ENVIRONMENT=staging, validate, then again with ENVIRONMENT=production — a separate VM, IP and database. The generated admin password is printed once and stored nowhere else.

6 · Ready vs not ready

Production ready
  • Isolated infra per customer, one command
  • TLS, session auth, TOTP 2FA, IAP-only SSH
  • BYOK keys encrypted at rest (pgcrypto); only last 4 chars returned
  • Tenant-scoped schema with cascade deletes
  • Audit log table
Not ready
  • No cloud provider integration at all
  • No google-cloud-*, boto3 or Azure SDK in pyproject.toml
  • cloud_accounts table is never written outside the seed
  • All pillar data served from lib/api/mock/*.ts
  • No automated backups attached by the script

What this means for a client conversation

Onboarding today delivers a fully working, isolated, branded pilot environment — genuinely useful for sales, POCs and validating UX with a real customer. It does not deliver a system observing their actual cloud estate. A client told "this is monitoring your environment" would be misled.

Closing the gap needs: a read-only role in the customer's cloud; ingestion for billing export, asset inventory and security findings; a scheduled sync writing to cloud_accounts; backend endpoints serving it; and NEXT_PUBLIC_DATA_SOURCE=api in the frontend build. None of that is scoped in the repo today.

7 · Operational constraints worth knowing

  • New GCP projects may be blocked — the current operator lacks billing.resourceAssociations.create.
  • The seed demo user cannot log in — 01-schema.sql has a placeholder bcrypt hash that reads like a working credential. Always use create_admin.
  • Postgres passwords are baked in at first init — regenerating .env.prod later breaks the backend; fixing it is destructive.
  • Region is effectively permanent — confirm residency before the first run.
  • Two provisioning paths exist — provision-customer.sh (proven) and the provision:customer CI job (untested).
  • Single VM means a reboot is downtime — no failover. Above ~99.5% SLA, Topology A will not hold (~$505–850/mo).
